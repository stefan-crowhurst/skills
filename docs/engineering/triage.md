## What it does

`triage` works through local markdown issues under `.scratch/`, moving each one through a small state machine of **triage roles** and leaving behind an agent-ready brief, a specific question, or a recorded rejection.

It is only for issues you did not create. Issues produced by [to-tickets](./to-tickets.md) are already agent-ready, so triage is the on-ramp for raw incoming work, not a second pass over your own plan.

## When to reach for it

You invoke this by typing `/triage`, and the agent will not reach for it on its own. Reach for it when local issue files contain raw bug reports or feature requests that need evaluation.

| What you have | Where to go |
| --- | --- |
| Raw reports in `.scratch/*/issues/` | `/triage` |
| A rough idea of your own | [grill-with-docs](./grill-with-docs.md) |
| A settled conversation to turn into a [spec](https://www.aihero.dev/ai-coding-dictionary/spec) | [to-spec](./to-spec.md) |
| A spec to split into agent-ready issues | [to-tickets](./to-tickets.md) |
| A confirmed bug that needs a root cause | [diagnosing-bugs](./diagnosing-bugs.md) |

## Prerequisites

[setup-matt-pocock-skills](./setup-matt-pocock-skills.md) must have configured the local tracker and status vocabulary. Issues use `Status:` for state, `Type:` for `bug` or `enhancement`, and `## Comments` for append-only notes.

## The state machine

Every triaged issue has one category in `Type:` and one state in `Status:`:

| State | Means |
| --- | --- |
| `needs-triage` | It needs evaluation. |
| `needs-info` | A specific answer is needed from the reporter. |
| `ready-for-agent` | It has a durable agent brief. |
| `ready-for-human` | It has a brief but needs human judgment, access, or testing. |
| `wontfix` | It is closed with the reason recorded in `## Comments`. |

Every appended triage note starts with `> *This was generated by AI during triage.*`. Appending under `## Comments` is the local comment operation. Setting `Status: wontfix` and appending the closing note is the local close operation.

Rejected enhancements also get a durable concept note in `.out-of-scope/`. Already implemented requests do not, because they are not rejected concepts.

## Verify before you brief

Before grilling, triage reproduces a bug where possible, runs the relevant local checks, searches for an existing implementation by domain concept, and checks `.out-of-scope/`. A confirmed reproduction makes a stronger brief than a guess. If the issue does not contain enough detail to try, `needs-info` is the honest result.

## Common questions

**Do issues from `/to-tickets` need triage?**

No. They already carry `Status: ready-for-agent` and the local issue structure. Triage is for incoming issues that need evaluation.

**Where does the agent brief go?**

It is appended as a structured note under `## Comments` in the issue file. The brief is the contract, while the original body and earlier comments remain context.

**How do I see what needs attention?**

Ask `/triage` to scan `.scratch/*/issues/*.md`. It groups files with no state, `needs-triage`, and `needs-info` with new comments, then lets you select one.

**What happens when an issue is rejected?**

Append the reason under `## Comments` and set `Status: wontfix`. For a rejected enhancement, also update the matching `.out-of-scope/` concept file.

## It's working if

- Every touched issue has one category in `Type:` and one state in `Status:`.
- Triage gives you a recommendation and waits for direction before applying it.
- The verification result is recorded before an agent brief is appended.
- Every appended note opens with the AI disclaimer.
- A rejected enhancement leaves a reusable `.out-of-scope/` concept note.

## Where it fits

`triage` is an **on-ramp**, not a step in the main chain. The main flow runs from an idea you had (grill, spec, tickets, implement, review), and `triage` is the parallel lane for work that arrived instead. It merges at the same place: a local issue file under `.scratch/` carrying `Status: ready-for-agent` with a brief on it, which [implement](./implement.md) picks up exactly as it would an issue from [to-tickets](./to-tickets.md). When a request needs sharpening before it can be briefed, `triage` runs [grilling](../productivity/grilling.md) and [domain-modeling](./domain-modeling.md) together, a round of questions at a time, so decisions land in `GLOSSARY.md` and the ADRs as they are made. When you are unsure which lane you are in, [ask-matt](./ask-matt.md) routes you.
